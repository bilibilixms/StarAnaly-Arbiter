# 第 7 周：集成与质量回归

## 核对第 6 周运行记录

`fox.md` 中第 6 周记录了前端构建通过，以及 CSV 分析和资料问答两个浏览器流程成功。CSV 的 300 / 200 / 500 与结构化结果一致；资料回答包含 14 天、第 3 行和文档名；删除后的引用接口为空。误把 Markdown 交给 CSV 输入框时页面给出文件类型提示，这是预期的输入校验，不是失败。

本次核对发现两个需要明确补齐的地方：

1. 第 6 周报告没有实际断开后端验证错误页与重试；因此第 6 周完整验收中的恢复场景尚无运行证据。
2. 第 5 周报告称 NUL、分段上限和部分控制器错误分支已有测试覆盖；仓库当时的测试并未覆盖这些具体分支。本次补充了对应测试和独立的 API 边界检查脚本。
3. 第 6 周报告写 CSV 文件显示 87 B，但对应代码版本中的 `fixtures/monthly-sales.csv` 是 88 B，且最新提交中的文件仍为 88 B。当次上传响应未保留，无法判定是记录笔误还是本机选取了不同文件。回归时请对比本地文件字节数、`GET /api/tasks/{taskId}/files` 的 `byteSize` 和页面显示值。

审查资料长行分段时还发现一个代码问题：按 UTF-16 字符位置切分可能拆开表情等补充平面字符。本次改为在代理对边界前结束当前片段，并添加回归测试。普通中文和英文检索行为不受影响。

## 本次检查范围

- 单元和 MVC 检查：资料编码、NUL、大小、分段数、Unicode 边界、检索参数、来源行号、资料接口错误响应，以及失败任务重新开始执行。
- 实际 API 检查：错误 CSV/资料、检索词边界、跨任务文件隔离、删除后无命中。`scripts/verify_quality.py` 会创建两个本地测试任务，不调用模型，也不删除既有任务。
- 日志与密钥静态核对：模型密钥只用于出站 `Authorization` 请求头；任务异常日志只写执行编号，公开错误只写状态或通用原因。真实运行日志仍需在测试机检查。

## 测试机执行

拉取代码、保持 MySQL 与后端运行，在仓库根目录执行：

```bash
mvn test
python3 scripts/verify_quality.py
python3 scripts/verify_knowledge.py
cd frontend && npm run build
```

`verify_quality.py` 预计输出四项“通过”。资料脚本复核 Unicode 分段修改没有影响模型工具闭环；前端构建复核接口类型与页面。将执行状态、失败原因和脱敏日志追加到 `fox.md`。

## 补做浏览器失败与恢复场景

1. 新建一个测试任务并打开详情页。停止后端进程，刷新页面：应看到连接失败提示和“重试”按钮。
2. 用原来的环境变量重启后端，点击“重试”：任务、文件和执行记录应重新出现，无需重建任务。MySQL 容器保持运行。
3. 如需验证模型失败与重试，在测试环境单独启动一个模型地址不可用的后端实例，再从页面提交问题；执行应进入 `FAILED` 并展示原因，输入框保留本次问题。恢复正常模型配置并重新提交后，应新增一次成功执行。不要在报告中记录真实密钥。

第 7 周是否完成，以测试机上的上述结果和日志核对为准；代码和静态检查本身不代替运行验收。
