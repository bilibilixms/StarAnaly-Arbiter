# 第 2 周：执行记录与步骤

> 状态：代码待用户测试机验证 · 对应 [开发规划](development-plan.md) 第 2 周

## 本次实现

每次向任务发送消息都会创建独立的执行记录。现有 `POST /api/tasks/{id}/messages` 保持同步返回模型回复；新增异步入口可立即返回执行编号，随后查询状态和步骤。两种入口共用任务锁、模型调用和消息保存逻辑，同一任务同时只允许一条执行中的记录。

Flyway V3 新建 `task_runs` 与 `task_run_steps`。执行记录保留任务 ID、输入长度摘要、状态、开始/结束时间和错误；步骤按 `stepNumber` 排序，当前包括 `MODEL_CALL` 和 `FINAL_ANSWER`。记录只存摘要，不存模型密钥或完整请求。服务重启时，遗留的执行中记录及任务会转为失败，保留已有步骤用于排查。

## API 契约

| 操作 | 方法与路径 | 结果 |
| --- | --- | --- |
| 创建异步执行 | `POST /api/tasks/{id}/runs`，请求体 `{"content":"请继续分析"}` | `202 Accepted`，`Location` 指向执行详情，响应含 `id`、`status=RUNNING` |
| 执行列表 | `GET /api/tasks/{id}/runs?page=0&size=20` | 按编号降序分页 |
| 执行详情 | `GET /api/tasks/{id}/runs/{runId}` | 状态、时间、摘要、`lastError` |
| 执行步骤 | `GET /api/tasks/{id}/runs/{runId}/steps` | 按 `stepNumber` 升序排列 |

无效内容返回 `400`；任务不存在或执行编号不属于该任务返回 `404`；同一任务已有执行中的请求返回 `409`。异步调用失败时，创建请求可能已经返回 `202`，之后在执行详情中看到 `FAILED` 和原因。失败后可再次创建新的执行，旧记录仍保留。原有消息查询接口继续展示成功完成的用户消息与模型回复。

## 测试机器上的验收

后端启动时先确认 V3 迁移成功，然后在仓库根目录运行：

```bash
mvn test
python3 scripts/verify_runs.py
```

第二个脚本会创建一条任务并调用已配置的 DeepSeek，轮询最长 120 秒，检查执行列表、步骤、任务状态和对话记录。密钥由后端读取，脚本不需要也不会打印密钥。还应在浏览器或 API 客户端确认旧的同步对话接口仍可使用；在模型请求尚未完成时，第二次向同一任务提交应返回 `409`。

若迁移或运行失败，请提供脱敏后的启动日志、HTTP 状态以及对应执行详情；不要发送密钥。第 3 周在这套步骤记录上加入工具请求、工具结果和调用限制。
